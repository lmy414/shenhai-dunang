# 深海的嘟囔 · 角色活动求索

「蓝色大肥鱼」系列的 AI 拟人角色收集网页小游戏。玩家通过单次或十连“求索”收集角色和武器，在独立的角色仓库、武器仓库中查看持有数量。

项目使用原生 HTML、CSS 和 JavaScript，采用 Canvas 绘制特效、Web Audio 合成音效。页面可直接在浏览器运行，进度保存在本机浏览器中，适合协作者从页面、角色资料和素材开始参与维护。

## 当前玩法

- 开放角色活动求索“深海的嘟囔”和武器活动求索“鲸落之勺”，点击左侧卡片切换。
- 角色池首页中央展示当期 UP 角色立绘，周围泛着金色粒子光，其余 9 名 5 星装在金色泡泡里漂浮在旁边；点击可查看档案。
- 支持单抽、十连、跳过演出、再次求索、卡池详情和 UP 预览；本次获得五星时，演出开场即有金光提示。
- 默认进入求索页，暂时移除大厅。底部两个独立按钮分别进入角色仓库、武器仓库，右上角按钮打开设置。
- 两个仓库各自显示累计持有数量，支持已获得 / 全部物品、星级筛选和档案详情；武器额外显示类型。
- 角色、武器按 3 星、4 星和 5 星分组。角色池 5 星 UP 为 DS娘，武器池 5 星 UP 为 DS娘专武“鲸落”。
- 角色池共有 10 名 5 星：出 5 星时 50% 为 DS娘，另外 50% 由其余 9 名 5 星平分。武器池只有一件 5 星，出金即为“鲸落”。
- 两个池共用保底设置和鲸币，五星、四星保底计数各自独立，互不继承；武器没有属性数值或装备系统。
- 五星基础概率为 0.08%，默认 90 抽保底。前 70 抽保持基础概率，第 71 抽起线性递增，第 90 抽必得；获得后重新计数。
- 玩家可在设置中将保底改为 1～10,000 的整数，预览对应的理论综合概率。默认 90 抽配置约为 1.3681%。
- 每个池连续 10 抽内至少获得 1 个 4 星或以上物品。
- 每抽消耗 1 枚鲸币，160 米饭可兑换 1 枚鲸币。
- 可查看最近 500 条求索记录，切换音效或重置存档。
- 求索页和仓库页右上角、米饭栏左边有“重置”按钮：确认后清空求索记录、角色仓库、武器仓库，以及两个卡池的已求索次数和保底进度；米饭、鲸币、保底设置和音效保留。

### 饭点活动 · 深海捞饭

点击抽卡页左侧“饭点活动求索”进入。俯视水下捕鱼：角色装在光泡里游动，点击水中任意位置，底部的发射器朝那里打出网弹，网弹到达后张开捕捞。

- 每撒一网消耗 1000 米饭，冷却 1 秒；米饭不设上限。
- 出现概率与角色池长期比例一致：5★ 约 1.37%（5★ 中 DS娘 占 50%），4★ 约 14.76%，其余为 3★。
- 网到时有概率逃脱：5★ 50%、4★ 20%、3★ 5%。逃走的角色只是被惊开，过一会儿继续在水里游，可以再捞。捞到获得 1000 / 5000 / 10000 米饭（3★ / 4★ / 5★）。
- 捞到的角色同时进入**角色仓库**（增加持有数量），但不写入求索记录。
- 天气每隔一两分钟随机变化，独立于水下光景，每种都会让捕捞变容易或变难：

| 天气 | 效果 |
| --- | --- |
| ☀ 晴朗 | 逃脱率 −20% |
| 🌧 细雨 | 4★、5★ 出现 ×1.3，逃脱率 +10% |
| ⛈ 雷暴 | 4★、5★ 出现 ×2，逃脱率 +40%，鱼游得更快 |
| 🌫 大雾 | 逃脱率 +25%，鱼游得更慢 |
| 〰 风平浪静 | 逃脱率 −10%，鱼游得更慢，4★、5★ 出现 ×0.85 |

- 武器池抽到的武器可放进捕鱼装备栏（1 格），获得网面、牢靠、招财、迅捷、节俭、引鲸、安眠等加成。
- 不限时，可随时暂停和结算；水下光景在清晨、白天、黄昏、夜晚、浑水之间每隔一两分钟随机切换。

### 可调保底与旧存档

设保底抽数为 `N`，基础概率为 `b = 0.0008`，固定概率区间为 `S = floor(7N/9)`。`n` 表示距上次出金的第几抽：

```text
n >= N：p(n) = 1
n <= S：p(n) = b
其余：  p(n) = b + (1 - b) × (n - S) / (N - S)
```

`N = 1` 时每抽必出五星。综合概率采用 `1 / E[T]` 计算，`E[T]` 为获得一名五星的理论平均抽数。这个值由完整出金分布计算，随保底设置改变；个人有限抽数的结果会有波动。

保底设置保存后对两个池立即生效，两个池的当前计数均继续保留。若计数已达到新的保底，下一抽必出五星。十连按顺序逐抽结算，出金后从第 1 抽重新计数。

旧存档新增 `hardPity` 字段，缺失时使用默认值 90。武器池字段为 `pool`、`wpity5`、`wpity4` 和 `wtotal`，缺失时补默认值。原有角色、武器、持有数量、货币、首充标记、记录与两个池的计数继续保留。旧记录没有 `p` 字段时归入角色池，武器记录使用 `p: weapon`。两个仓库与累计五星数量读取 `owned`，不受最近 500 条求索记录的上限影响。重置存档会清空两个仓库与计数，并将保底恢复为 90。

## 本地运行

```bash
git clone https://github.com/lmy414/shenhai-dunang.git
cd shenhai-dunang
```

快速查看可以直接打开 `index.html`。日常开发建议通过本地 HTTP 服务访问，保持固定的地址和端口，便于检查资源加载与存档。

已安装 Node.js 和 npm 时，在项目根目录运行：

```bash
npx --yes serve . --listen 3000
```

打开终端显示的地址，通常是 `http://localhost:3000`。当前项目没有 `package.json`，无需安装项目依赖，也没有 `npm run build` 命令。

## 协作流程

1. 开工前确认本人开发分支和已有修改，查看相关 Issue。新建分支时先更新远端引用，再从 `origin/main` 创建；继续已有任务时保留当前分支的工作。
2. 两位协作者分别在自己的分支和本地目录中开发，一次提交围绕一个主题。
3. 修改前确认涉及的规则、界面和素材。新增素材时登记来源、作者及授权条件，见 [NOTICE.md](NOTICE.md)。
4. 本地预览并完成相关检查，将用户可见变更记入 [CHANGELOG.md](CHANGELOG.md) 的“未发布”部分，交给本次任务发起人本地复核。
5. 复核通过并获得明确授权后，再提交或推送本人分支。推送后核验远端提交 SHA；需要 PR 时写明修改和验证结果，由维护者审阅并处理合并到 `main` 的工作。

分支归属、授权范围和冲突处理规则见 [Agent 协作指引](AGENTS.md#双人分支协作)。

提交说明可使用 `feat:`、`fix:`、`docs:` 或 `ci:` 前缀，后接具体改动。请保留现有署名，避免把本地存档、凭据、缓存或生成目录提交到仓库。

### 提交前检查

修改 `app.js` 后，先执行语法和规则检查：

```bash
node --check app.js
node --test tests/gacha.test.cjs
```

规则检查覆盖支持范围内的保底边界、90 抽曲线、首次出金分布、角色与武器旧存档、独立计数、重复持有数量和四星保底。浏览器画面、演出与交互仍需按下表实际预览。

根据修改范围检查以下行为，并在 PR 中写清实际完成的项目：

- 页面、背景、角色立绘和图标正常加载，浏览器控制台没有新增错误。
- 单抽、十连、跳过、结果确认和再次求索可正常结束。
- 鲸币扣减、米饭兑换、模拟支付、保底计数和概率显示符合代码规则。
- 刷新后可读取存档；需要检查重置时，使用独立浏览器配置或测试存档。
- 修改布局或演出时，检查桌面宽屏和手机窄屏，确认按钮热区与显示位置对应。
- 只改文档时，检查相对链接、命令和发布说明是否与仓库一致。

## 版本发布

生产站点为 Cloudflare Pages 项目 `shenhai-dunang`。现有工作流仅在**发布正式 GitHub Release** 时部署，普通代码推送、仅推送标签和保存 Release 草稿都不会触发该工作流；预发布版本会跳过部署任务。

维护者也可以指定开发分支提交作为 Release 来源。此时须明确标签的目标提交，并核验远端 SHA。分支发布会更新生产站点，Git 的 `main` 不会自动合并；下列步骤为通常的主干发布流程。

1. 合并准备发布的修改，确认本地检查通过。
2. 将“未发布”记录整理到新的版本号和日期下，再提交、推送到 `main`。
3. 在 [GitHub Releases](https://github.com/lmy414/shenhai-dunang/releases) 创建版本，使用指向待发布提交的标签，例如 `v1.3.0`，填写更新说明并发布为正式版本。
4. 在 [GitHub Actions](https://github.com/lmy414/shenhai-dunang/actions/workflows/deploy-pages.yml) 查看执行结果。工作流会检出标签代码、检查 JS 和素材、整理 `dist/`、部署并检查访问状态。
5. 上线后再打开生产地址，核对本次修改的实际页面效果。工作流成功只代表其中的自动检查通过。

部署使用仓库 Secrets 中的 `CLOUDFLARE_API_TOKEN` 和 `CLOUDFLARE_ACCOUNT_ID`，凭据由维护者管理。失败后先查看日志，临时故障可在对应运行记录中重试失败任务；代码问题应修复并发布新版本，避免移动已经发布的标签。

当前的 `Build dist/` 步骤只复制静态文件。以后需要编译或资源处理时，在此处接入构建命令，并继续将结果输出到 `dist/`，复用后续部署流程。
