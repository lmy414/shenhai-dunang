> 适合完全不想碰命令行的人：你只管说人话，AI 帮你敲命令。

项目介绍、目录和协作约定见 [README](../README.md)，历史变更见 [更新日志](../CHANGELOG.md)。Agent 开工前应先读根目录的 [AGENTS.md](../AGENTS.md)。

## 0. 核心思路

你不用记 git、gh 这些命令。你需要的只有三样：

1. **一个 GitHub 账号**：项目放在这里，相当于网盘加版本记录。
2. **一个能操作电脑的 AI 助手**：比如 Cursor、Claude Code、Codex CLI，或者 Grok Bot 这类能跑命令的 AI。
3. **会说清楚自己想要什么**：剩下的交给 AI。

比如在聊天框里说「把这个 PR 合并了」「看看最近有没有新 issue」，AI 会自己去执行，再回来汇报结果。

## 1. 第一次准备（大约 15 分钟，只做一次）

### 1.1 注册 GitHub
打开 https://github.com 注册一个账号，然后把**用户名**告诉仓库管理员（lmy414），由他把你加成协作者。之后你的邮箱会收到邀请，点 **Accept** 接受。

### 1.2 装一个 AI 编程助手（任选其一）
| 工具 | 适合谁 | 说明 |
|---|---|---|
| **Cursor** | 最推荐新手 | 像记事本一样打开项目文件夹，右侧直接跟 AI 聊天，AI 能改代码、跑命令 |
| **Claude Code / Codex CLI** | 不怕黑窗口的人 | 在终端里和 AI 对话 |
| **Grok Bot 等托管 AI** | 完全不想装东西 | AI 用它自己的电脑帮你操作，你只在聊天里下指令 |

### 1.3 让 AI 帮你装好环境
打开 AI 助手，直接把下面这段话发给它：

> 帮我在这台电脑上准备好 GitHub 开发环境：
> 1. 检查并安装 git 和 GitHub CLI（gh）；
> 2. 运行 gh 登录，需要我在浏览器里点授权的时候告诉我；
> 3. 设置 git 用户名为「（你的名字）」、邮箱为「（你的邮箱）」；
> 4. 把 lmy414/shenhai-dunang 克隆到我的「文档」文件夹，然后用编辑器打开它。

中间 AI 会给你一个 8 位验证码，并让你在浏览器里登录 GitHub、点授权。**这是唯一需要你亲手操作的步骤**，因为登录只能本人来做。

## 2. 日常维护：照着说就行

下面每一条都可以直接复制给 AI，括号里换成你自己的内容。

### 改东西、上线
| 你想做的事 | 对 AI 说 |
|---|---|
| 开工前同步 | 「先把仓库拉到最新」 |
| 改内容 | 「把 Kimi 角色的台词改成……」「背景图换成桌面上的 new_bg.jpg」 |
| 预览 | 「帮我在浏览器里打开预览看看效果」 |
| 保存并上传 | 「没问题了，提交并推送，提交说明写：（改了什么）」 |
| 记录变更 | 「把这次已完成的改动补进 CHANGELOG.md 的未发布部分」 |
| 一条龙 | 「拉最新 → 帮我把（需求）改好 → 让我预览 → 我说 OK 后提交推送」 |

### 管理项目
| 你想做的事 | 对 AI 说 |
|---|---|
| 记待办或 bug | 「在仓库开个 issue：手机上按钮太小，点不到」 |
| 看待办 | 「列一下这个仓库还没关的 issue」 |
| 做完关掉 | 「#3 已经修好了，回复一句然后关掉」 |
| 发版本并上线 | 「把待发布记录整理好并提交，基于确认的提交创建新标签，再发布正式 GitHub Release，检查自动部署结果和线上页面」 |
| 看别人改了啥 | 「最近一周谁改了什么？用中文总结给我」 |
| 审 PR | 「看看有没有新 PR，说说改了什么、有没有风险，我同意了再合并」 |

### 出问题了
| 情况 | 对 AI 说 |
|---|---|
| 改坏了 | 「撤回上一次提交」或者「回到昨天能正常玩的版本」 |
| 推送失败 | 「推送报错了，帮我看看怎么回事并解决」 |
| 冲突了 | 「先解释双方的改动和冲突原因，确认应该保留的行为，再解决冲突」 |
| 看不懂提示 | 直接把报错截图或文字丢给 AI：「这是什么意思？怎么办？」 |

## 3. 跟 AI 打交道的小技巧

1. **说结果，不说步骤**：说「让角色立绘在手机上不要被切掉」，比说「改 CSS 的 max-width」好用得多。
2. **重要操作让它先汇报**：比如「先告诉我你打算怎么改，我同意了再动手」。删除、强推、合并这类操作尤其要这样。
3. **一次一件事**：一次只提一个需求，做完、预览完、推送完，再提下一个。
4. **让它解释**：随时可以问「刚才那条命令是干嘛的？」，问多了自然就懂了。
5. **按服务支持的方式授权**：GitHub 登录可走浏览器授权。Cloudflare 自动部署使用仓库 Actions Secrets，密钥直接填入服务的安全输入框，避免写进聊天、代码和日志。

## 4. 两个人一起维护的规矩

- 每次开工先说「拉到最新」，改完就说「提交推送」，别攒着。
- 同一个文件尽量别两个人同时改。
- 大改动可以说「开个新分支来做」，确认没问题再说「合并回 main」。
- 实在搞不定，就把问题原样描述给 AI，或者联系 lmy414。

## 5. 上线说明

- 正式版本通过 GitHub Release 自动部署到 Cloudflare Pages，工作流位于 `.github/workflows/deploy-pages.yml`。
- 普通推送、仅推送标签和保存 Release 草稿都不会触发该工作流。发布为预发布版本时，部署任务也会跳过。
- 准备上线时，先确认代码和更新日志已提交，再创建指向该提交的新版本标签，发布正式 Release。
- 发布后查看 [GitHub Actions](https://github.com/lmy414/shenhai-dunang/actions/workflows/deploy-pages.yml)，确认检查、部署和访问验证均成功，再到生产站点检查实际效果。
- 执行耗时取决于任务排队和上传情况，以运行记录为准。
- 当前站点为纯静态页面，工作流中的 `Build dist/` 只整理发布文件。以后需要编译时，再在这个步骤接入构建流程。
- 详细步骤、部署失败处理和凭据名称见 [README 的版本发布说明](../README.md#版本发布)。
